# W8-Library — Agent Guide

FRC Team 3467 (Windham Windup) shared robot library plus an example robot project that exercises it.
Java 17, WPILib 2026 (GradleRIO), command-based, AdvantageKit logging, CTRE Phoenix 6, PhotonVision,
Grapple LaserCAN, Lombok.

The people maintaining this code are high school students. Write code a student can read, debug at
a competition, and learn from: clear names, small methods, Javadoc on public API, and comments that
explain *why* (physics, units, vendor quirks) rather than restating the code.

## Repository layout

```
src/main/java/frc/lib/        Reusable library (the product). Hardware-agnostic building blocks.
  io/<thing>/                 IO interface + one implementation per hardware/sim backend
  devices/                    Thin wrappers that own an IO + its logged inputs (BeamBreak, DistanceSensor, ...)
  mechanisms/                 Motor-driven mechanisms: flywheel/, linear/, rotary/ (Real, Sim, Visualizer)
  posestimator/               Pose estimation + swerve odometry
  autos/, commands/           Auto container, reusable command types
  util/                       Tunables, logging helpers, geometry, Device port records, CAN config thread
src/main/java/frc/robot/      Example robot that uses the library (also the integration test bed)
  subsystems/<name>/          <Name>.java subsystem + <Name>Constants.java (config + factory)
  commands/, autos/           Robot-specific commands and autonomous routines
src/main/generated/           Generated FlatBuffers sources — never edit by hand
src/main/deploy/              Files deployed to the roboRIO (AprilTag layouts, etc.)
src/test/java/                JUnit 5 tests, package-mirrors src/main/java
vendordeps/                   Vendor library JSONs — change only via WPILib vendordep tooling
```

`frc.robot.BuildConstants` is generated by the gversion plugin on build; do not edit it.

## Build, test, simulate

Use `./gradlew` (Git Bash / Linux / macOS) or `gradlew.bat` (PowerShell / cmd).

```
./gradlew build -x test     # compile (includes Error Prone and AdvantageKit @AutoLog processing)
./gradlew test              # JUnit tests (HAL simulation, no hardware needed)
./gradlew simulateJava      # run the robot in the WPILib simulator
```

CI (`.github/workflows/build.yml`) runs build, test, then `spotlessCheck` on every push. Spotless has
no formats configured right now, so it passes trivially — formatting is enforced by review, not
tooling. Follow the style below by hand.

Before finishing any change: it compiles, `./gradlew test` passes, and nothing under `generated/` or
`vendordeps/` was touched unless that was the task.

## Core architecture (the one idea to internalize)

Every piece of hardware is split into three layers so the same robot logic runs on a real robot,
in physics simulation, and in AdvantageKit log replay:

1. **IO interface** (`frc.lib.io.<thing>.<Thing>IO`) — a nested `@AutoLog` inputs class plus
   `default` no-op methods for reading sensors and commanding outputs.
2. **IO implementations** — `<Thing>IO<Hardware>` (e.g. `MotorIOTalonFX`, `BeamBreakIODIO`) and
   `<Thing>IOSim`. All vendor classes (CTRE, Grapple, PhotonVision) live only here.
3. **Consumers** — devices, mechanisms, and subsystems that hold the *interface* type, call
   `io.updateInputs(inputs)` then `Logger.processInputs(name, inputs)` every loop, and read state
   only from `inputs`.

The runtime mode (`Constants.currentMode`: `REAL`, `SIM`, `REPLAY`) picks the implementation in a
factory. In `REPLAY`, an anonymous `new <Thing>IO() {}` is used — this is why IO interface methods
are `default` no-ops rather than abstract or throwing.

## Java style

Match the surrounding file. When in doubt, these are the conventions the codebase follows:

- **Formatting**: 4-space indent, 8-space continuation indent, 100-column lines, braces on the same
  line (see `style.xml`). Don't reformat code you aren't otherwise changing.
- **License header**: new `.java` files start with the GPLv3 header used in
  `src/main/java/frc/lib/io/motor/MotorIO.java` (`Copyright (C) 2026 Windham Windup`).
- **Imports**: no wildcards in new code. Groups separated by blank lines, in this order: static
  imports; third-party (`au.`, `com.`, `edu.`); `frc.`; `lombok.`; `org.`; `java.`.
- **Units**: use the WPILib units library (`Angle`, `Distance`, `AngularVelocity`, `Voltage`,
  `Current`, `Time`, ...) in fields, parameters, and return types, created via static imports
  (`Rotations.of(1.0)`, `Inches.of(3)`, `Volts.zero()`). Convert to `double` only at a vendor or
  WPILib-math boundary with `.in(Unit)`. Never pass bare `double`s whose unit lives only in the name.
- **Naming**: `UPPER_SNAKE_CASE` for `static final` constants, `camelCase` for everything else,
  descriptive names (`leftMotorVolts`, not `lmv`).
- **Javadoc**: every public class and public method gets Javadoc with `@param` / `@return`. Every
  field in an `@AutoLog` inputs class gets a one-line `/** ... */` comment.
- **Lombok**: use `@Getter` for simple accessors, `@NoArgsConstructor(access = AccessLevel.PRIVATE)`
  for constants/static-only classes, `@Getter(lazy = true)` for singletons. Don't add other Lombok
  annotations casually; keep generated behavior obvious to students.
- **Records** for immutable data carriers (`PID`, `Device.CAN`, `TalonFXFollower`,
  `RotaryMechCharacteristics`).
- **`switch`**: prefer arrow form (`case REAL -> { ... }`) in new code.
- **Optional** for values that may be absent (`Optional<Distance>`, `Optional<AbsoluteEncoderIO>`);
  never return `null` from a public getter.
- **Logging**: log keys are `name + "/Thing"`. Use `Logger.recordOutput` for derived values and
  `@AutoLogOutput(key = "...")` on getters. Don't use `System.out` or `SmartDashboard.put*` for
  telemetry — log through AdvantageKit.
- **Errors**: fail fast in constructors with `IllegalArgumentException` for bad config (see
  `Device.CAN`, `Mechanism.withRadius`). Report hardware faults at runtime with WPILib `Alert`s, not
  exceptions.
- Don't leave large commented-out blocks in new code; delete it (git remembers).

## Git workflow

- `dev` is the main branch; open PRs into `dev`.
- Branch names: `<issue-number>-<kebab-description>` (e.g. `258-generic-vision-subsystem`) or a
  short kebab description when there is no issue.
- Commit messages: short, imperative, sentence case (`Add acceleration modeling to RotaryMechanismSim`).
